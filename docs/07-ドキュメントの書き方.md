# 07 このドキュメントの書き方（残しておくべきこと）

このフォルダ（`~/files/プロジェクト/simple-yurii-pkm/`）は、**次の AI・次のセッションが
この PKM を触るときの唯一の引き継ぎ資料**。何かを触ったら必ずここに足す。

原則は 1 つ: **「次の自分が詰まる足場」を全部残す**。困らせない。

## 1. 何を残すか（判断基準）

次のどれか 1 つに当てはまったら、**迷わずドキュメントへ追記する**。

- **罠・嘘のような事実** … ドキュメント・コメントと実装が食い違っている、
  「直したはずが反映されない」類。→ `06-引き継ぎ.md`
- **エンジンの取り違え** … 実行時に実際に呼ばれる関数がどれか。→ `03-同期の規則.md`
- **焦ったこと / 遠回りしたこと** … 2〜3 手で行き止まって別のルートへ逃げた話。→ `06` か `03`
- **整形ルール** … ノートがどう書かれるべきか。→ `02-ノート形式.md`
- **確認手順** … 「どう確認したか」のコマンド。→ `06`
- **環境の事実** … 場所・パス・remote・ブランチ。→ `01-概要` / `05-データとリポジトリ`
- **テストの既知の壊れ** … 変更前から落ちているテスト。→ `06`
  （重要: 自分の変更で壊れたと思わず进行調査し直さないため）

逆に**残さないもの**: コードから機械的に読めること、1つずつ列挙したキー表（`04` に既有）、
一回限りの作業ログ。

## 2. どこに残すか

| 内容 | 場所 |
| --- | --- |
| ノートの書き方・整形ルール | `02-ノート形式.md` |
| 同期の決まり方・エンジン | `03-同期の規則.md` |
| 環境・パス | `01-概要.md` |
| リポジトリ・push ルール | `05-データとリポジトリ.md` |
| 罠・確認手順・テストの壊れ | `06-引き継ぎ.md` |
| 「ドキュメントの書き方」自体 | `07-ドキュメントの書き方.md`（このファイル） |

**新しいファイルを増やしすぎない。** 01〜06 のどれかに寄せる。増えるのは本当に
新しい章が必要なときだけ。

## 3. 規範と事実の書き分け

- **規範**（これから守る）: `02` / `03`。`〜する` / `〜は無い` / `〜に入れる`。
- **事実**（いまそうなっている）: `06`。必ず **日付と症状** を添える。
  例: 「2026-09-27: `sync_vault` を直しても `update` で反映されなかった。
  原因: `update` は `simple_sync()` を呼ぶ。」

## 4. 2 つのコピーを同期する

このフォルダは 2 箇所に実体がある。**どちらかを直したら必ず両方へ反映する**。

1. 本体: `~/files/プロジェクト/simple-yurii-pkm/`（Git 管理外・作業する場所）
2. 複製: `~/.vim-simple-yurii-note/simple-yurii-note/docs/`
   （GitHub `Yurii7812/simple-yurii-note` に公開している）

```bash
cp ~/files/プロジェクト/simple-yurii-pkm/*.md \
   ~/.vim-simple-yurii-note/simple-yurii-note/docs/
cd ~/.vim-simple-yurii-note/simple-yurii-note \
  && git add -A && git commit -m "docs: 仕様ドキュメントを更新" && git push origin main
```

`~/.config/opencode/skills/pkm-system/SKILL.md` にも読む順（01〜07）のリストがあるため、
**ファイルを新設したらそこにも足す**。他のセッションは skill 経由で入るので、ここが入口。

## 5. 項目の書き方

- 1 項目 = 1〜2 行。長い説明はしない。
- **症状 → 原因** の順で書く。「〜しようとしたら〜だった」ではなく
  「〜が反映されない。原因は〜という関数を直していた」。
- 実際に通ったコマンドがあれば、そのまま貼る（次のセッションがそのまま再現できる）。
- 確信のないことは「未確認」と書く（誤った確信を次のセッションに引き継がないため）。

## 6. 姿勢: なるべく書く

既定を「書かない」側に置かない。**迷ったら書く**。書き上げるまで待つより、
その時点のメモが 1 行でも残っている方が、次のセッションに都合がよい。

- **1 文でも書く。** 断片でも、日付つきでも、`（たぶん）` でもよい。
- **同じことを 2 箇所に書いてもよい**（例: 落とし穴を `03` と `06` の両方に置く）。
  重複しても困らない。片方だけを誤って読むより、両方読んで重なったところを見るほうが安全。
- **理由を書かないまま結論を書かない。** 「直した」ではなく
  「反映されない。原因は `sync_vault()` を直していた（`update` は `simple_sync()` を呼ぶ）」。
- **何かを覚えたら必ず 1 つ書き足す。** 覚えたつもりで忘れるのがいちばん多い失敗。
- **分からなかったこと・迷ったことも書く。** 「Index を Parent に入れられるのか分からなかった。
  実装を見てから分かった」。これが次回いちばん効く。
- **失敗した手も残す。**（テストがどこで落ちた、revert したか所、など）
- ただし**ファイル新設は控えめ**（第 2 節）。足すのは中身であって、ファイルを分けることではない。

短くまとめることより、**次の自分が詰まらないこと**を優先する。
